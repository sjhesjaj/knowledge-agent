## 1. R1　解析失败的回退答案绕过交付校验

### 复现（修复前）

`repro_rework.py::r1` 脚本化两次模型响应：第一次是非 JSON 文本，第二次是
`answer()` 返回的「每年享有 99 天带薪年假。[来源99]」。唯一证据只写 5 天。

```text
validate_answer(bogus)      = (False, 'citation_out_of_range')
answer_structured delivered = '{"answer": "…99 天带薪年假。[来源99]"}'
```

比验收报告描述的更糟：`answer()` 不解析 JSON，把整个信封原样返回了。无论哪种形态，
结论一致——**未经校验的内容被交付**。

### 修复

`rag.py`：删掉 `except` 分支里的 `return answer(...)` 早返回，让它与结构化分支
汇合到函数末尾同一处 `validate_answer`。

```python
    except (json.JSONDecodeError, KeyError, TypeError):
        result = answer(question, results, history)
        structured = False
    # 回退分支自己已经用掉第二次生成调用，不再叠加证据复查
    if structured and needs_evidence_recheck(...):
        ...
    ok, _reason = validate_answer(result, results, question)
    return result if ok else UNGROUNDED_ANSWER_MESSAGE
```

**单题生成调用上限仍是 2**：结构化 1 次（+ 复查 1 次），或结构化 1 次 + 回退 1 次，
两者不叠加。

### 修复后

```text
answer_structured delivered = '根据现有资料无法确定。'
```

真实 API 回归见第 2 节的 `test_stream_and_plain_agree_on_body_terminal_event_and_storage`
与 `ApiDeliveryTests`，覆盖**格式错误**而不只是格式正确的 JSON。

## 2. R2　两接口失败语义不一致

### 复现（修复前）

同一问题、同一证据、注入同一段「99 天年假。[来源1]」：

| 普通接口 | SSE |
|---|---|
| 最终「根据现有资料无法确定。」，落库 2 条 | 99 天正文已逐字发出；随后 error；不落库 |

### 修复：改为「验完再发」

原实现是「边发边验」——只能拦住越界编号，拦不住复述问题、缺引用和无依据数量，
因为那三类要看完整答案才能判定，判定出来时正文已经在读者屏幕上。已删除逐段放行
窗口（原 `CITATION_HOLD_LIMIT` / `_release_validated`），改为：

- JSON 信封仍逐块解析，**传输层错误照旧在读到的那一刻抛出**（中途 error、缺 done、
  非法转义、拼接不一致）；
- 可见正文在整段解析完成并通过 `validate_answer` 之前一个字都不发；
- 交付校验失败**不抛异常**，而是发出与普通接口逐字相同的拒答文案，
  让调用方照常发 `done` 并落库。

### 修复后

```text
plain  final body : '根据现有资料无法确定。'
stream shown text : '根据现有资料无法确定。'
stream terminated : None（正常结束）
```

API 层新增 `test_stream_and_plain_agree_on_body_terminal_event_and_storage`：
**读取全部 delta**、检查终态事件、比对两个会话的数据库记录，四项分别断言——
正文相同、被拒文本从未出现、终态是 `done` 而非 `error`、落库内容与条数一致。
另加 `test_a_transport_failure_still_errors_and_persists_nothing`，确保拒答路径
没有把真正的传输错误一起吞掉。

`InterfaceConsistencyTests` 也已加强：原来只断言「普通拒答 / 流式抛错」，
现在断言**两条接口最终正文逐字相同**。验收报告指出旧断言弱于计划要求，属实。

### 一个必须说明的取舍，以及一处原有断言的处理

**代价**：首段可见正文不再是「模型吐出第一个字」，而是「整段生成完成」。
这是为一致性付出的确定代价，没有两全方案——任何在校验前就发出的文字都收不回来。

**但有一个例外，需要验收方确认是否接受**：`results` 为空时仍然逐段放行。
理由是缓冲的目的是保证正文与**证据**一致，没有证据就没有会被推翻的断言——
`no_citation` 本就跳过，`ungrounded_quantities` 直接返回空。产品链路到不了这里
（编排链路无证据时由证据策略提前拒答，legacy 链路知识库为空时 409）。

这一分支同时使 `tests/test_streaming.py::test_streams_visible_content_and_requires_done`
（原有 630 项之一，以 `results=[]` 调用并断言逐块产出）**保持通过、未被修改**。
按计划「不得放宽原有断言」的要求，我没有改它；但我也说明白：这个分支的存在
部分是为了不与该断言冲突。**如果验收方认为应当无条件缓冲，请判定，我照改**——
那将需要主 agent 裁定该原有断言与本轮能力定义的冲突。

首段可见文字延迟的实测数据尚未重新采集（需真实模型，见第 6 节）。

## 3. R3　否定范围与有效请求组合

### 复现（修复前）

四例全部失败：

| 题面 | 期望 | 修复前 |
|---|---|---|
| 我不需要概览，只核对培训总结提交期限的原文。 | `document_only` | `wiki_document` |
| 不用介绍全貌，直接引用报销单笔金额的审批分界。 | `document_only` | `wiki_document` |
| 我只要 apr-3002 当前审批状态，不用解释审批制度。 | `system_only` | `document_system` |
| 明白，暂时没别的需求，回见。 | `direct` | `document_only` |

### 修复：三处语义问题，不是四句话

1. **否定只作用于原文类标记**。第一轮把否定范围只接在 `DOCUMENT_EXACT` /
   `PRECISION` / `AUTHORITY` / 子句引用上，概览标记、政策语境和版本变化仍是无条件
   匹配。现在这三类同样走 `_contains_any_unnegated`，「不需要概览」「不用解释审批制度」
   才真正生效。
2. **`总结` 是动词也是名词**，只有动词在请求概览。`总结制度变化` 是请求，
   `培训总结提交期限的原文` 里的「总结」是文档名——第一例真正的误触发点在这里，
   不在被否定的「概览」上。新增 `SUMMARY_VERB_PATTERN`：动词读法出现在子句开头或由
   `帮/请/先/再/来/给/我` 引出，或后接 `一下/下/一遍`；名词读法前面是它自己的主题词。
3. **告别语缺少「应答 + 没别的 + 道别」这一组合**。补入 `回见`、`明白`、`知道了`、
   `没别的`、`就这些`、`问完了` 等。安全性由既有规则保证：`_is_direct` 仍要求
   **每个**子句都不提出请求，所以 `我不明白年假规定` 因为有政策名词仍是请求。

### 修复后

四例全部正确。新增变体测试（`tests/test_route_variants.py`，均为新写句子，
未复用上述已曝光题面）：

| 测试类 | 覆盖 |
|---|---|
| `NegationCoversEveryChannelTests` | 拒绝概览 4 例、拒绝解释制度 3 例 |
| `SummaryWordSenseTests` | `总结` 动词 3 例 / 名词 3 例 |
| `AcknowledgedSignOffTests` | 应答式告别 4 例，以及同样词汇包着真实问题时仍需检索 3 例 |

公开集无回归：`blind_v2` 100%、`dev` 100%、`validation_v1` 100%、`holdout` 97.5%。

**已曝光题的口径**：上述四句已在验收报告中公开，此后视为已曝光回归题，
不再计为未见题。下一次独立性声明需补充等覆盖的新题。

## 4. R4　中文数值归一化

### 复现（修复前）

```text
_cn_number_to_arabic('四十二') = '4十2'
证据「库存为42件。」+ 回答「库存为四十二件。[来源1]」→ ungrounded_quantity（误拒）
```

原实现是逐字替换，只特判了两字形式。

### 修复

改为按位值计算，覆盖 0–999；无法识别的写法**原样返回**，让它对不上——
宁可漏判一次，也不要把解析不出来的串当成某个具体数字去比对。

```text
十→10  十一→11  十五→15  二十→20  二十一→21  三十→30
四十二→42  九十九→99  一百→100  一百零五→105  二百三十四→234
```

修复后该答案通过；对真实无依据数值的拦截未放宽（R5 的 99 天仍被拦下）。
相等与不相等两侧都有测试。

## 5. R5　问句里的数字被当成支持依据

### 复现（修复前）

证据 5 天，问题「每年有 99 天年假吗？请核对原文」，回答断言「每年享有 99 天带薪年假」
→ `validate_answer` 返回 `(True, ok)`。原实现把 `quantities(question)` 无条件并入支持
集合，于是**用户的猜测成了确认该猜测的依据**。

### 修复

问句里的数字只在两种情形下算复述而非断言：

1. 答案同时给出**同一量词、且证据支持**的数值（在对比或纠正）；
2. 答案把它放在假设或否定语境里（`HYPOTHESIS_CUES`：如果/若/假设/按你说的/不是/并非…）。

两条都不满足，就是在把猜测当事实说，判为无依据。

### 修复后

| 情形 | 结果 |
|---|---|
| 断言猜测值「每年享有 99 天」 | `(False, ungrounded_quantity)` ✔ 拦下 |
| 纠正「不是 99 天。每年享有 5 天。」 | `(True, ok)` ✔ 放行 |
| 条件「如果按你说的 99 天…原文写的是 5 天」 | `(True, ok)` ✔ 放行 |
| 证据支持的数值「满三年增加至 8 天」 | `(True, ok)` ✔ 放行 |

四种情形均有测试，覆盖任务单要求的「来源明确否定用户猜测」与「回答仅引用用户假设作
条件」两类。
