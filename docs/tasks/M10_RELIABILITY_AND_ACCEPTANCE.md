## 1. 本轮目标与完成定义

让用户用自然表达提出复合问题时，系统能选全必要通道、检索到相关证据、回答各个有依据的子问题，并在缺少依据或能力未开放时准确说明。

本轮集中解决四件事：

1. 修复概览、精确条款、业务状态混合请求的路由遗漏。
2. 改善 Wiki 及原文证据相关性，减少答非所问。
3. 改善回答完整性、拒答和引用，验证普通接口与 SSE 接口。
4. 更新 README 与演示说明，使项目介绍对应实际代码和本轮验证。

完成必须同时满足：既有功能回归通过、公开数据集达标、新验收题达标、实际 API/SSE 路径通过、资料更新生命周期无回归、文档真实。测试数量增加或子 agent 自报完成，均不能替代这些条件。

本轮不包含：接入真实企业数据库、登录鉴权、多实例部署、写操作工具、扩大多 SKU 查询能力、增加自主循环、更换技术栈或向量数据库。保留这些后续方向即可。

## 4. A：组合路由与边界判断

### 预期行为

1. 概览、原文依据、业务状态可以同时成立；根据全部有效请求组合通道。
2. 一个请求包含问候、背景叙述或时间词时，不能遮蔽真正的问题；纯寒暄也不应误触发知识检索。
3. 正确处理否定的局部作用范围，例如排除原文要求的表达，不应被孤立的“原文”关键词反向触发。
4. 区分制度中的数值与系统当前数值；同句或不同分句中出现两类数值时，不能只保留 System。
5. 缺少 SKU、多个 SKU、订单/审批未开放等请求，应进入对应的固定边界行为。维持本轮既有能力边界，不通过扩充业务操作来提高成绩。
6. 保留 `plan_request()` 的纯函数性质、八种路由、既有顺序和最多三步限制。保留现有可注入 fallback 契约，不默认增加模型路由调用。

### 实现要求

- 先用最小失败用例定位现有分句、意图组合、否定范围或边界识别的具体问题，再作修改。
- 优先修正语义组合逻辑；不能靠持续罗列失败题整句完成修复。
- 不把所有请求都送进三个通道。验收同时检查少选和多选。
- 增加问句顺序交换、标点替换、背景插入、实体替换、否定位置变化的行为测试；这些测试不应只是复刻内部实现。

### 阶段门槛

- V2 80 题：整体和 Macro Accuracy 均至少 90%；每类路由至少 80%；Boundary Accuracy 至少 85%。
- 对应整数下限：整体至少 72/80，每类至少 8/10，45 道边界题至少 39/45。
- 所有既有路由/规划回归通过；固定边界答复不得调用生成模型。

## 5. B：证据相关性与复合问题覆盖

### 预期行为

- Wiki 返回的事实与用户主题相关，不能仅因通用字词相交就把无关页面排在前面。
- 请求多个政策事实时，证据应覆盖各个有依据的子问题；涉及库存的内容不能挤掉政策证据。
- 原文中的数字、适用对象、条件、时间范围和审批对象需完整保留。
- 证据缺失时保持为空或进入现有拒答流程；不能用排名分数冒充已校准的置信度。
- 查询使用本次请求捕获的 Wiki/知识版本。不得为提高相关性破坏已实现的更新、发布和清空一致性。

### 实现要求

- 分别验证静态样例 Wiki 和动态编译后 Wiki。命中动态 Build 只说明链路接通，不能代替相关性判断。
- 保留 `Chunk → Evidence` 适配边界；不整体替换 RAG 实现。
- 如需拆解复合检索问题，在现有检索适配层内部做有界处理。子查询数最多 3 个，不增加执行器工具调用次数，不引入循环追问或模型重规划；最终结果仍遵守原调用方的 `top_k`。
- 如修改排序，说明它解决哪类误召回，并记录改善和退化案例。

### 阶段门槛

- 对验收者冻结的 20 道单主题、有明确原文依据的问题，静态 Wiki、动态 Wiki、Document 三条检索路径分别统计。
- 每条路径 Relevant Hit@3 至少 90%（18/20）；三条路径合计 Top-1 相关率至少 90%，且任一单路径至少 80%。Wiki 用默认 top_k=3；Document 使用默认返回结果的前 3 条计算 Hit@3。
- Relevant Hit@3 定义：前三条至少一条证据包含该题事先标注的必要事实，并可追溯到指定原文位置；仅同主题或同标题不算命中。
- 另用复合问答集检查多事实覆盖；不能把上述单主题相关性指标描述成复合问题完整率。
- 文档更新、跨文件退役、回退、清空和重启恢复的既有测试全部通过。

## 6. C：回答完整性、拒答、引用和流式一致性

### 预期行为

1. 对有证据的各个子问题逐项回答，不能仅复述问题，也不能用过短输出限制挤掉关键事实。
2. 引用既要编号有效，也要在语义上支持对应结论。源文件出现过某个数字，不意味着它可以用于另一个结论。
3. 无依据的问题明确拒答；证据复查不能把原本正确的拒答改成捏造答案。
4. 部分问题缺依据时，遵循现有证据充分性和拒答契约，不用常识补齐缺失部分；本轮不另增“部分成功”的新协议。
5. 普通接口和 SSE 在同一证据、同一脚本化模型响应下，最终正文、引用、拒答决策与持久化结果保持一致。
6. 对真实模型，两条接口不要求逐字相同，但均须覆盖必要事实、正确引用并满足相同能力边界。

### 实现要求

- 同时检查 `answer_structured()`、`answer_stream()` 和 API 消费路径，不能只优化离线评测入口。
- 新增保护必须挂在真正使用的路径；不能以调用了未接入产品的校验函数作为验证结果。
- 流式校验需说明检查发生在输出前、过程中还是结束后。不能在内容已经发送后才声称防止了错误内容暴露。
- 保留 SSE 事件及负载契约、错误时不落库、会话锁和知识版本检查。若需要内部缓冲来实现校验，必须记录对首段可见文字延迟的影响。
- 不新增回答重试循环；不超过既有有界生成/复查次数。既有超时与错误处理不能弱化。

### 阶段门槛

V2 回答集仍使用原评测器，40 题连续运行 3 轮；每轮单独检查，不能只挑最好一轮：

| 指标 | 本轮要求 |
|---|---|
| 总通过率 | 每轮至少 90%，即 36/40 |
| Answer Success Rate | 每轮至少 90%，即 20 道可答题至少 18 道通过 |
| False Refusal Rate | 每轮最多 10%；另列出相对本轮新测基线新增的误拒题 |
| Unanswerable Refusal Rate | 每轮至少 90%，即 12 道不可答题至少 11 道正确拒答 |
| Boundary Message Accuracy | 每轮至少 90%；8 道题意味着必须 8/8 |
| Citation Index Validity | 每轮至少 95%；所有发现的越界编号须列入失败清单 |
| Expected Fact Hit Rate | 每轮至少 90% |
| Cross-run Stability | 按原评测器口径至少 90%；另列稳定失败，稳定地答错不算质量达标 |

- 对冻结的可答题，人工或独立验收逐条核对关键结论与其引用；关键结论须得到所引证据支持，不能用“编号有效”替代此检查。
- 独立 API/SSE 验收选择 8 道可答题覆盖七种非 direct 通道路由（额外一道复合问题），加 4 道边界或拒答题。两条接口均用真实本地模型跑一轮：可答题各至少 7/8；4 道边界/拒答题必须全部正确。脚本化响应的两接口一致性用例必须全部通过。
- 性能比较使用同设备、同模型实际版本、同样资料和暖机方式：本轮同路径 p95 相对新测基线增幅不超过 25%；冷启动单列，不混入暖机结果。SSE 首段可见正文、总耗时和模型调用次数分别报告。超出上限即未达标，不能改口径掩盖。

## 8. 主 agent 的独立验收流程

### 8.1 候选冻结与环境隔离

1. 接收子 agent 的修改文件清单、补丁、新增文件和自测报告。
2. 在查看候选 diff 或运行候选输出前，按本计划的能力定义编制并冻结验收题及判定依据；实现 agent 不得看到题面和标注。本计划公开题型与门槛，不公开新题。
3. 锁定候选：有提交则记录 SHA；没有提交则记录 HEAD、工作区 diff 的 SHA-256，以及每个新增文件的 SHA-256。不能只用未变化的 HEAD 代表未提交代码。
4. 在新隔离副本中还原候选，包括未提交修改和新增文件。仅 `git archive HEAD` 会遗漏这些内容，不能当作候选验收。
5. 隔离数据库、Wiki 根目录、模型缓存路径和测试输出，使用空闲端口。任何导入 `api` 的操作都发生在隔离源代码副本内。
6. 记录 Python/依赖版本、Ollama 版本、实际模型标识或 digest、机器配置、语料和题集哈希。对比阶段串行使用本地模型，避免并行推理竞争影响延迟。

### 8.2 验收题组成与独立性

- 路由：新增 80 题，八类各 10 题，至少 40 道覆盖复合表达、否定、背景插入、顺序变化和能力边界。采用 A 的相同比例门槛；边界整数门槛按实际分母向上取整。
- 问答：新增 40 题，保持 20 可答 / 4 policy_refuse / 8 generation_refuse / 8 boundary 的分布；采用 C 的指标与 3 轮规则。
- 检索：另增 20 道单主题题，提前标注原文位置、必要事实与相关性标准，按 B 验收静态 Wiki、动态 Wiki 和 Document。
- API/SSE：从验收集抽取上述 12 题，不能只演示实现者提供的成功样例。
- 新题只依赖原始资料和现有能力契约，不能根据候选回答补写标注或放宽事实要求。先做来源核对、歧义核对和与历史题的重复/模板重合检查，再冻结哈希。
- 使用既有 schema 和冻结评测器；相关性与真实接口验收使用主 agent 独立的外部工具，不由实现者修改评分规则。
- 这些是“实现方未见的验收题”，不宣称完全独立双盲。V2 已公开，本轮只能称为公开回归集。
- 若返修时向实现者提供某个新题的完整题面和期望，该题之后计为已曝光回归题；再次宣称独立新题验证时应补充等覆盖的新题并重新冻结，不能仍叫未见题。

### 8.3 实际检查顺序

1. 检查修改范围、冻结文件哈希，以及是否存在读取题库、答案硬编码或放宽测试。
2. 运行语法检查、原有完整测试与新增行为测试。
3. 运行公开路由/回答回归；Dev、Validation、Holdout 中已有结果也需作前后比较，列出新增回归。
4. 检查检索相关性、新题路由、新题回答与真实 API/SSE。
5. 在临时环境做一次真实模型动态编译与文档更新演练，验证发布后新事实可查、被替代旧事实不再进入回答；失败回退、重启和清空以现有故障注入/生命周期测试另行验证。
6. 核对文档、失败清单和性能数据，给出通过或不通过结论。

模型不可用、依赖缺失或接口没跑通，记为“未完成验证”，不能记为通过。未通过时指出失败类别、原因、需要修改的边界和复验范围；保留每轮原始记录。
