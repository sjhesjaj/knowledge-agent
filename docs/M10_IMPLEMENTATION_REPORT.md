### 2.1 A：组合路由与边界判断

**保留不变**：`plan_request()` 仍是纯函数，八种路由、Wiki→Document→System 的固定
顺序、最多三步、可注入 fallback 契约、fallback 不能选 `direct` 全部未变；未默认
增加任何模型路由调用。

新增的是**语义类别**，不是失败题的整句：

1. **告别语**（`SOCIAL_CLOSING_MARKERS`）。原表只有「就到这儿」这类固定说法，
   「聊到这儿」「回头聊」「先忙」「准备下班」都不算社交，于是一句告别被送去检索原文。
2. **整体概览的三种说法**：概括动词（概括/总览）、整体范围（整套/从头到尾/来龙去脉/
   框架/全貌）、走查动词（过一遍/理一遍）。
3. **精确性要求**（`DOCUMENT_PRECISION_MARKERS`）。「要准确的」「一字不差」「原样」
   本身不指名任何文档，但它们说明调用方不接受转述——这正是原文通道要服务的请求。
   这类词经常单独成句（`……，要准确的`），所以按子句判定而不是整句判定。
4. **审批主体提问**（`AUTHORITY_QUESTION_PATTERN`）。「由谁签字」「谁审批」问的是
   制度怎么规定，不是某条记录现在归谁；因此动词限定在批准类（签/批/审/核/负责/
   决定/授权/同意/把关），刻意排除「处理」——「谁在处理我的订单」是状态问题。
5. **时长阈值提问**（`QUANTITY_INTERROGATIVE_PATTERN`）。「几小时内」「几个工作日」
   问的是制度设的阈值。量词必须是度量词：通用量词「个」试过后删掉了，因为
   「覆盖哪几个方面」是在数概览条目，不是阈值。
6. **可用性提问**与**完成状态提问**：「还有货吗」「够不够」「走完了没」和
   「还有多少」问的是同一件事，只是没带数字。
7. **记录标识**（`RECORD_ID_PATTERN`）。`ord-1002` 这类标识说明「哪一条记录」，
   它补的是对象那一半而不是状态那一半，因此**单独出现不选 System**——
   `ABC-123 是什么意思` 问的是这个编号什么意思，仍然不走 System。
8. **否定的作用范围**。中文也把否定放在宾语之后：`具体条款先别给我` 把「条款」提前，
   否定落在本该提供它的动词上。原来只向前看，于是把这句读成了「要条款」。
   现在双向判定，但**向后只认供给类动词**（给/发/列/提供/展开/贴/附/抄/罗列/念），
   所以 `原文别省略`——要求给更多而不是更少——不受影响。
9. **补齐两处词表里本来就该有的成员**：`大体` 补进概览弱标记（与既有的 `大概`/`大致`
   同族，之前漏了）；`存量`/`余量`/`现货`/`备货`/`在库` 同时进对象表和取值表——这类词
   一个词就把「问谁」和「问什么」都说全了，`现在的存量` 后面并没有第二个名词可补。
   歧义词的配对规则没有放宽。

**取舍与被删掉的尝试**（都是先加后删，理由记录在代码注释里）：

- `讲清楚`/`说清楚` 不是概览请求。它们要求把**当下这件事**说清楚，
  `引用原文讲清楚盘点口径` 要的是原文。加上后 validation 集出现 2 例回归，删掉。
- `那套`/`这套` 是回指，不是「全部」。`我们那套旧系统好用多了` 因此被误判成概览请求。
  只保留明确表示「全部」的 `整套`/`全套`。
- `要求` 从「强条件标记」移到「政策语境标记」。`整体是怎么要求的` 是概览，不是在问
  适用条件；留在强标记里会让每个这样的请求都多拉一条原文通道。
- 子句引用 `那条`/`那几条` 只认代词用法（后面是句末、`的` 或人称代词）。
  `这条线` 里的 `条` 是量词，不是在引用条款。

`chat_orchestration._is_inventory_question` 也扩了词表：`现在这边货还够吗` 过去回
「当前版本仅支持库存查询。」——它问的正好是唯一开放的那一项，只是没给 SKU。
这个函数只在 Planner 已经选了 System 且没找到 SKU 之后才被调用，所以扩宽是安全的，
退货政策一类的问题根本到不了这里（有测试守住）。

### 2.2 B：证据相关性与复合问题覆盖

**保留不变**：`Chunk → Evidence` 适配边界未动，RAG 实现未整体替换，执行器工具调用
次数未增加，没有引入循环追问或模型重规划，`top_k` 仍是调用方的上限。

两处改动：

1. **`planner.document_focus()`（新增公开函数）+ `document_adapter` 调用它**。
   复合请求里常有一条文档答不了的子句。整句交给检索时，问题分解器会把它也拆成一个
   子问题并分配一个证据名额，然后用当时得分最高的片段把这个名额填掉。政策证据不是
   被比下去的，是被挤出预算的。因此检索前先去掉「只有业务系统能回答」的子句和纯寒暄；
   **只有 Wiki 能回答的子句予以保留**，它提供主题词，对词法检索有帮助。
   没有可去掉的内容时**原样返回同一个字符串**，因此普通单问句路径逐字节不变。
2. **`rag.drop_padding_results()`**。BM25 已经有把握到可以跳过 Embedding 与重排时，
   远低于最佳命中的结果是为凑满 `top_k` 返回的，不是因为它匹配。阈值取最佳命中的
   20%，最佳命中永远保留。

**改善与退化案例**（同一语料，`top_k=4`）：

| 请求 | 本轮前返回的章节 | 本轮后 |
|---|---|---|
| `设备遗失几小时内要上报？Sku-C300 当前存量报我一下` | 设备领用、**工作时间**（BM25 0.00） | 设备领用、离职交接、办公区域管理 |
| `信息安全概览、公共网盘那条的原样条文、SKU-A100 实时库存，三样都要` | 信息安全、账号与权限、**软件安装**、**薪资发放** | 信息安全、账号与权限 |
| `年假先给个总览，满三年增加到几天那句准确措辞发我，再看下 Sku-C300 最新库存` | 请假制度、工作时间、**员工建议与申诉**、**绩效考核** | 请假制度、工作时间 |
| `单笔超过 2000 元由谁签字，要精确的；SKU_B200 目前的存量报一下` | 费用报销、培训学习 | 费用报销、培训学习、考勤与迟到 |

第一例和第四例是**退化案例**，如实记录：收敛掉 System 子句后，问题从两个子问题变成
一个，检索路径从「每个子问题取一条」切换到「单问句取前 N 条再剔除填充」，噪声条数因此
反而多了一条。两例的第 1 条证据都仍然正确。第四例里的「培训学习」不是填充——那一节
确实写着「2000 元」，词法上是真匹配。**这类「数字对得上、结论对不上」的召回不是检索
能解决的**，它由 C 阶段的数量依据核对兜住（见 2.3）。

### 2.3 C：回答完整性、拒答、引用与流式一致性

新增 `rag.validate_answer()`，普通回答与流式回答**共用同一套判定**，全部是纯函数：

| 判定 | 依据 |
|---|---|
| 空答案 | 没有可交付内容 |
| 复述问题 | 去标点后与问题相同，或整句被问题包含 |
| 引用编号越界 | `[来源 N]` 的 N 不在 `1..证据条数` 内，即指向不存在的证据 |
| 有证据却无引用 | 给了证据、不是拒答、却一处来源都没标 |
| 无依据的数量 | 答案里的「数字＋量词」在证据和问题里都找不到 |

明确拒答永远可交付，且不受后两项约束。**这五项都是可判定的形式问题；本函数不判断
结论与所引证据在语义上是否相符**，那仍需人工或独立验收逐条核对。

**「有证据却无引用」这一条是在真实接口自测中发现后补上的。** 第一轮 API/SSE 自测里，
模型对两道题返回了「根据用户问题，需要从资料中提取……我将逐一检查资料中与问题相关的
信息。」——它不复述问题、不含数字、也没有越界编号，前面三项全部放行，于是这段分析过程
被当成答案交付了。补上这一条之后，这类输出会先触发那一次证据复查，复查提示词明确要求
标注 `[来源1]`；仍不合格才拒答。

**该规则也做了离线假阳性标定**：把基线与候选各 3 轮、共 174 条「有证据且调用了模型」
的答案重放一遍，规则只在 4 条上触发，**这 4 条全部是冻结评测器本来就判为失败的答案**
（`answer_v2_006` 三轮的问题复述，以及 `answer_v2_020` 一轮的同类分析过程），
被评测器判为正确的答案一条都没有被误挡。

**对 legacy 链路的影响（有意为之，如实记录）**：交付校验挂在生成层，因此
`mode=legacy` 的请求也会经过它。legacy 链路的路由、检索与 SSE 协议均未改动，但一段
引用越界、或有证据却不标来源的回答，现在同样会变成拒答。把这道闸只装在新链路上，
等于让旧链路继续可以发出编造的引用，所以没有那样做。README 与演示指南里原先
「关闭时行为完全一致」的说法已相应更正。

**「数字＋量词」的必要性**：资料写的是「加班时长可按 1:1 转为调休」。字符 `1` 是有的，
`1 倍` 没有。基线里模型据此答出「工作日加班的加班费按 1 倍计算」——拿一个数字去支撑
另一个结论。只看裸数字挡不住，绑上量词才挡得住。中文数字归一为阿拉伯数字，
`个工作日`/`工作日`、`个小时`/`小时` 视为同一量词。

**上线前的假阳性标定**：把基线 3 轮共 120 条模型答案离线重放一遍，
该规则命中 3 条（三轮里的同一道题，即上面那条幻觉），**被冻结评测器判为正确的答案
一条都没有被误挡**。标定脚本与原始输出见第 7 节。

**证据复查次数未增加**。原来只有「看起来像拒答」会触发那一次复查，现在复述问题和
无依据数量同样触发——**触发条件放宽了，次数没变，仍是至多一次**，有测试守住
（首轮答案合格时只有 1 次生成调用，触发复查时 2 次，不会有第 3 次）。复查失败时的
回退值也改了：原来固定退回首轮结果，如果首轮是复述问题，退回去等于把它放行；
现在只有首轮本身是拒答才退回它，否则退回拒答文案。

**流式接口的校验分两处，作用不同，不能混为一谈**：

- **输出前（逐段）**：来源标注在放行之前先验编号。越界编号在读者看到之前就中止本次
  流式回答。这是**真正的阻止**。代价是把一段最长 24 个字符的文本推迟到标注闭合之后
  再发——只在遇到 `[` 之后才扣留，按字符计而不是按秒计，对首段可见文字的延迟影响
  见第 5 节实测。
- **结束后（整段）**：复述问题、空答案、无依据数量要看完整答案才能判定，到那时正文
  已经发出去了。这是**检测，不是阻止**：它让本次回答以 `error` 事件收尾、不落库、
  不发 `done`，而不是声称读者没看到过那段文字。

普通接口在同样判定失败时改为拒答并落库。**两条接口判定规则相同，但流式收不回已发出
的文字，这个差异是真实存在的，本报告不掩盖它。** 一致性测试覆盖了可以一致的部分：
同一份证据、同一段脚本化模型输出下，两条接口对「这段文本能不能交付」的结论一致。

**保留不变**：SSE 事件与负载契约、错误时不落库、会话锁、知识版本校验、既有超时与
错误处理，全部未改。没有新增回答重试循环。

**可答题从 5/8 提升到 8/8**，三处路由漏选（`api_wiki_document` 漏原文、
`api_wiki_document_system` 漏 Wiki、`api_compound_three_channel` 漏原文）全部修复。
边界题 `api_boundary_system_limited`（`ord-1001 现在什么状态`）基线走成 `document_only`
并调用模型花 5.40s 得到一句拒答，候选走 `system_only` 并在 0.05s 返回固定能力边界文案
——**这个修复同时省掉了一次模型调用**。

**一处必须说明的延迟代价**：单题最大耗时从基线 8.77s 变成候选 15.59s，出现在
`api_compound_three_channel`。原因不是链路变慢，而是**这一题基线本来就漏了一条通道**：
基线只走 `wiki_system`（漏原文），候选走满 `wiki_document_system`，证据更多、提示词更长、
生成也更长。换句话说，这段增量是「把这道题答对」的成本，不是同等工作量下的退化。
p50 反而从 3.99s 降到 3.54s。回答集口径下的 p95 增幅为 +7.7%，在 +25% 上限内（见 5.3）。

### 6.2 唯一未达标项：SSE 侧的 `api_refusal_unsupported`（3/4）

题目 `公司年终奖发几个月工资，要准确的`，资料里确实没有这条，应当拒答。

| 接口 | 模型首轮输出 | 结果 |
|---|---|---|
| plain | 「根据用户问题，需要确定……我需要在提供的资料中查找相关信息。」 | 交付校验判 `no_citation` → 触发证据复查 → **拒答并落库**，判定通过（10.80s，两次生成调用） |
| stream | 同上 | 正文已逐字发出；结束后校验失败 → 发 `error`、**不落库、不发 `done`** → 本轮自测判为失败（8.29s） |

**这是设计上的真实局限，不是评分口径问题，如实记录**：

- 流式**做到了**：不落库、不发 `done`、以固定错误文案收尾，下游不会把这段文字当成
  一次成功回答保存下来；
- 流式**做不到**：把已经发出的文字收回，或改成拒答。因此在真实模型下，两条接口对
  这道题的**最终正文与持久化结果不一致**——任务说明第 6 节第 5 条要求的一致性，
  在脚本化响应下全部通过（`InterfaceConsistencyTests`），在真实模型的这一失败形态下
  没有达到。第 6 条对真实模型只要求「覆盖必要事实、正确引用并满足相同能力边界」，
  这道题两条接口都没有输出错误答案，但流式给的是 `error` 而不是拒答，
  **是否算「满足相同能力边界」，由验收方判断，本报告不替它下结论**。

**为什么没有改成整段缓冲**：缓冲能让两条接口完全一致，代价是首段可见正文从 2.32s
推迟到总耗时。实测总耗时 p50 3.32s、最大 14.90s（三通道复合题），也就是最坏情况下
读者要对着空白等待近 15 秒。为一个约 1/12 出现、且已经安全失败的形态付这个代价，
判断上不划算，所以**保留当前设计并在此写明**，由验收方裁定是否接受。

计划允许缓冲但要求记录首段可见文字的延迟影响：当前设计的影响是**只在遇到 `[` 之后
扣留，最多 24 个字符，直到该来源标注闭合**。这一点由
`StreamingLatencyCostTests` 三项测试测量（无标注时逐段原样放行；标注前的正文在标注
闭合之前就已发出；非来源标注的方括号超过窗口后放行），实测首段可见 p50
2.32s 与基线 2.36s 相当，未见可测量的代价。

### 6.3 静态 Wiki 与动态编译 Wiki 分别验证

| 路径 | Relevant Hit@3（门槛 ≥90%） | Top-1 相关（单路径 ≥80%） |
|---|---|---|
| 静态样例 Wiki（`wiki_pages/`） | 19/20　95.0% | 18/20　90.0% |
| 动态编译 Wiki（真实模型编译） | 20/20　100% | 19/20　95.0% |
| 原文 Document | 20/20　100% | 20/20　100% |

三路径合计 Top-1 相关率 **95.0%**（门槛 ≥90%），任一单路径均 ≥80%。

判定口径按计划：前三条里至少一条证据**既包含该题事先标注的必要事实、又能追溯到指定
的原文章节**；仅同主题或同标题不算命中——所以静态 Wiki 那道落空题的三条证据虽然全部
来自正确章节，仍判为未命中（见 8.1 R4）。

**动态 Wiki 是真编译出来的**，不是命中兜底样例：评测器用真实模型跑
`compile_wiki_fast`，页面结构与标题由模型规划，claim 正文逐字取自来源片段。
6.1 的接口验证也在编译发布之后进行，`build-0001` 即该次编译产物。

**复合问题的多事实覆盖单独计量**，没有拿上面的单主题相关性冒充：
`blind_v2` 回答集里的复合题由冻结评测器的 Expected Fact Hit Rate 衡量，
三轮为 100% / 100% / 95.0%（基线 85% / 90% / 90%）。

### 6.4 关键结论与其引用的人工逐条核对

计划要求：「关键结论须得到所引证据支持，不能用『编号有效』替代此检查」。
`dump_citation_support.py` 把候选第 1 轮 20 道可答题的答案与它**实际引用的那几条证据
全文**并排导出（`docs/m10-selftest/citation-support.md`），逐条读过。

**结论：20 题的关键结论全部由其所引证据支持**，没有出现「引用编号有效但那段话并不
支撑这句话」的情况。数值型结论（30 天、2000 元、3 个月、2 天、2 小时、10 分钟 / 2 次、
90 天、42 件 / 0 件 / 7 箱）都能在被引用的那一条里逐字找到。

读的过程中发现两处**校验挡不住、但应当记录**的瑕疵：

1. **`answer_v2_017` 把 SKU 写短了一位**：答案写「SKU-A10: 42 件」，正确编号是
   `SKU-A100`。数字与引用都对，冻结评测器按 `42` 匹配也判过。当前校验只核对
   「数字＋量词」，**不核对标识符**，所以漏过。这是一个真实的小缺陷，如实记录。
2. **`answer_v2_006` 用了资料以外的常识做归类**：资料只说「国内出差由部门负责人审批，
   境外出差还需总经理审批」，答案自行判定「深圳属于国内、新加坡属于境外」。
   规则本身引用正确，归类是通用常识而非编造的制度条款；但严格按提示词
   「只能使用资料里的事实」来说，这一步越了线。属于可接受范围还是需要收紧，
   留给验收方判断。

另外可以看到：多数题都有未被引用的证据条目（例如 `answer_v2_018` 的 5 条里有 3 条
没被引用），这正是 2.2 说的词法相关但结论无关的召回。本轮它们没有导致错误答案，
但确实还在提示词里。

### 8.2 `answer_v2_002` 误拒的定位

一句拒答文案，可能是模型自己拒的，也可能是交付校验把不合格的答案换成了拒答——
两者字面完全一样，光看输出分不出来。所以用 `diagnose_case.py` 把这道题重放若干次，
每次记录：模型首轮原始输出、`validate_answer` 对它的判定、是否触发证据复查、
最终交付了什么，以及最终那句拒答的来源。

重放 5 次，5 次全部正常作答，**一次都没有触发交付校验**：

```text
question : 单笔 2500 元的报销，除了直属主管还需要谁审批？门槛金额是多少
route    : document_only   sources: 2

--- attempt 1..5（五次完全一致）---
  model calls      : 1
  first answer     : '单笔 2500 元的报销，除了直属主管还需要部门负责人审批。门槛金额是 2000 元。[来源 1]'
  validate(first)  : ok=True reason=ok
  delivered        : （同上，原样交付）
```

**结论：这次误拒不是本轮新增校验造成的。** 首轮答案合格、只用一次生成调用、
`validate_answer` 判定 `ok`，交付校验根本没有介入。第 3 轮那次拒答是**模型自己拒的**
——在计数运行里这道题用掉了 2 次生成调用，说明首轮就是拒答、证据复查也维持拒答，
两次都是模型的判断。温度为 0 并不保证跨进程完全可复现。

顺带说明检索侧：这道题的第 2 条证据是「工作时间」一节，与问题无关。它的 BM25 得分
高于最佳命中的 20%（问句里的「2500 元」「多少」与该节的数字、时间表述有词法重叠），
因此没有被尾部剔除挡掉。这是 2.2 里说过的局限——**词法相关但结论无关的召回，不是
检索层能判掉的**。它没有导致错误答案（模型引用的是来源 1），但它是这道题偶发拒答的
一个合理诱因：提示词里多了一段无关文本。

**没有为此放宽任何校验**。放宽会同时放行幻觉（`answer_v2_028` 那一类），代价远大于
一道题在 1/3 轮里保守拒答。改进方向写在 8.4 第 5 条。

### 8.4 下一步建议

1. **把「结论 ↔ 引用」的语义相符做成可自动判定的检查**，哪怕先只覆盖数值型结论
   （数值必须出现在**它所引用的那一条**证据里，而不是任意一条）。这是本轮
   `ungrounded_quantities` 的自然下一步：现在它对所有证据求并集，收紧到「按引用编号
   逐条核对」能挡住「引用 1、事实来自 4」这一类。
2. **给跨子句的指代补一层有界处理**，覆盖 R1 的两题形状：无自身内容的子句
   （`想对比一下`、`三样都要`）继承邻句意图。需要先有一批变体题证明它是规律而不是特例。
3. **补齐样例 Wiki 的覆盖**，或在文档里明确「静态 Wiki 只覆盖 4 个主题」，避免把
   数据缺口误读成检索缺陷（本轮已在 README 写明，但样例本身没有补）。
4. **消除测试对 `data/` 的隐式依赖**（见第 4 节提示），让接口验证与单元测试可以在
